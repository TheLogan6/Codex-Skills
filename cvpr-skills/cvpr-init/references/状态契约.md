# `.cvpr` 状态契约

## 文件职责

| 文件 | 职责 |
|---|---|
| `project.yaml` | 项目身份、研究范围、目标、资源、边界和历史接入状态 |
| `state.yaml` | 当前长期阶段、进度摘要、开放问题、阻断、偏离和下一任务 |
| `tasks.jsonl` | 原子任务的追加式账本 |
| `claims.yaml` | 候选论文 Claim 与证据关系 |
| `decisions.jsonl` | 经讨论确认的研究决策 |
| `runs.jsonl` | 实验运行记录 |
| `deviations.jsonl` | 目标、范围、资源或执行偏离 |
| `start.yaml` | `cvpr-start` 保存种子输入、补充文献、问题状态、全部候选 IDEA、多 Agent 审查、讨论轮次与最终 IDEA；初始化时不是必需文件 |
| `goal.yaml` | `cvpr-goal` 在 IDEA 确认后创建的最终核验契约；初始化时不是必需文件 |
| `plan.yaml` | `cvpr-plan` 在 Goal 和开发基础确认后创建的阶段计划；初始化时不是必需文件 |
| `result.yaml` | `cvpr-result` 在 DO 最终判定后创建的三审复核、用户呈报与后续路由契约；初始化时不是必需文件 |
| `paper.yaml` | `cvpr-paper` 在论文阶段创建的当前稿件、Result 快照、原子能力产物、审计与用户确认索引；初始化时不是必需文件 |
| `paper/terminology.yaml` | 论文术语、缩写、指标、单位和公式符号账本 |
| `paper/numbers.yaml` | 正文数字到 Run、统计表与图形源数据的追溯账本 |
| `paper/citations.yaml` | 论文论断、引用和支持等级账本 |

`.yaml` 模板采用 JSON 表达形式；JSON 是 YAML 1.2 的有效子集，并能由标准库确定性解析。所有 `.jsonl` 文件每个非空行必须是一个 JSON 对象。

`project.yaml.success_criteria` 保存初始化阶段已知的概括性标准。存在已确认的 `goal.yaml` 后，以其中的具体核验协议和验收判据作为 `cvpr-plan` 与最终验收的权威目标；两者冲突时不得静默覆盖，应记录偏离并请求用户裁决。

`project.yaml.working_idea` 只保存便于进度讨论的当前摘要。存在 `.cvpr/start.yaml` 后，以其中的候选证据、审查记录、用户讨论和最终 IDEA 为研究启动权威记录。`cvpr-result` 的 IDEA 自我纠正循环必须引用该文件，不能仅从摘要恢复历史候选。

`plan.yaml` 保存经用户确认的长期阶段基线，不保存命令级原子工作，也不作为高频执行状态文件。进入具体阶段后，由 `cvpr-do` 将该阶段拆成原子任务并追加到 `tasks.jsonl`；实际阶段状态保存到 `state.yaml.stage_statuses`。计划阶段不得提前用大量原子任务替代阶段结构。

项目根目录下的 `cvpr_workspace/` 不是 `.cvpr` 状态目录的一部分。它用于保存可执行的单次检查、稳定入口、固定配置、正式核验包装、分析代码和 `入口清单.yaml`；核心研究实现仍保留在真实项目代码结构中。

论文 Claim 继续以 `.cvpr/claims.yaml` 为权威来源。`cvpr-paper` 不得在
`.cvpr/paper/` 下创建第二套 Claim 账本。论文稿件、LaTeX、表格、图形和复现材料
保存在 `cvpr_workspace/paper/` 或其引用的项目目录中，`.cvpr/paper.yaml` 只保存状态、
版本、快照和证据定位。

当 Result 的冻结 `snapshot_id`、纳入 Run、指标定义、数据划分、统计规则、Goal
或 Claim 证据边界发生变化时，依赖旧输入的论文产物必须标记为 `stale`。保留历史，
不得仅因路径相同而静默继续使用。

## 状态语义

- `proposed`：已提出但尚未开始。
- `running`：正在执行。
- `executed`：已产生结果，尚未通过完成标准验收。
- `accepted`：证据满足完成标准，已验收。
- `blocked`：因明确阻断项不能继续。
- `rejected`：结果不满足目标或不支持当前方向。
- `superseded`：经明确决策由后续方案取代。

不得从 `running` 直接把历史工作推断为 `accepted`。任务验收必须保存可定位的 `evidence_refs`。

## 长期阶段

阶段名称允许随研究类型扩展，但模板建议使用：

1. `intake`
2. `literature-and-problem-map`
3. `research-start`
4. `goal-contract`
5. `stage-planning`
6. `baseline-and-feasibility`
7. `method-and-engineering`
8. `experiments-and-analysis`
9. `evidence-audit`
10. `result-review`
11. `paper-drafting`
12. `manuscript-review`

`cvpr-init` 只识别和记录阶段，不执行阶段工作。

## 执行期状态

`state.yaml` 1.1 增加：

```json
{
  "active_plan": null,
  "current_stage_id": null,
  "last_accepted_stage_id": null,
  "stage_statuses": [],
  "execution_workspace": {
    "manifest_file": "cvpr_workspace/入口清单.yaml",
    "status": "not_created"
  },
  "goal_assessment": null
}
```

- `active_plan`：执行开始后保存 `plan_id`、`version` 和 `plan_file`；
- `current_stage_id`：当前唯一主执行阶段，可以为 `null`；
- `last_accepted_stage_id`：最后一个有证据的已验收阶段；
- `stage_statuses`：Plan 每个阶段的运行时状态和证据，不能反向改写原 Plan；
- `execution_workspace.status`：允许 `not_created`、`proposed`、`active`、`superseded`；
- `goal_assessment`：由 `cvpr-do` 作出的最终逐项 Goal 判定；状态允许 `passed`、`not_met` 或 `indeterminate`，未进入最终审计时为 `null`。`cvpr-result` 只能复核和挑战，不能直接改写。

存在已接受 Plan 并开始 `cvpr-do` 后，`active_plan` 必须与该 Plan 一致，`stage_statuses` 必须且仅能覆盖全部阶段。阶段为 `accepted` 时 `evidence_refs` 不得为空。

旧版 1.0 状态仍可由 `cvpr-init` 回读，但进入 `cvpr-do` 前必须展示 1.1 迁移差异并获得用户确认。不得临时假设缺失字段存在。

## 原子任务最小字段

`tasks.jsonl` 是追加式事件快照。新任务记录至少包含：

```json
{
  "id": "TASK-001-E001",
  "task_id": "TASK-001",
  "revision": 1,
  "previous_record_id": null,
  "event": "created",
  "created_at": "2026-07-28T10:00:00+08:00",
  "phase": "research-start",
  "stage_id": null,
  "status": "proposed",
  "objective": "核对候选问题在近年文献中的研究缺口",
  "inputs": ["研究记录/候选问题.md"],
  "boundaries": ["不修改代码", "不运行实验"],
  "deliverables": ["研究记录/问题核对报告.md"],
  "acceptance_criteria": ["覆盖约定检索范围", "结论可追溯到来源"],
  "evidence_refs": [],
  "suggested_capability": "后续研究启动技能"
}
```

- `id` 是全文件唯一的记录 ID；
- `task_id` 是跨状态变化保持稳定的逻辑任务 ID；
- `revision` 必须从 1 连续递增；
- `previous_record_id` 指向同一任务上一条记录；
- 每条记录保存完整快照，不覆盖旧行；
- `accepted` 任务的 `evidence_refs` 不得为空。

兼容读取旧版只有 `id` 的任务记录：将其解释为同名逻辑任务的修订 1。为旧任务追加状态时必须使用新事件格式。

## 已确认结论

`state.yaml.confirmed_findings` 的每项必须同时包含：

```json
{
  "statement": "可复述的事实或结论",
  "evidence_refs": ["相对路径、提交、运行 ID 或其他稳定定位"]
}
```

没有证据定位的内容放入 `open_questions` 或 `history_reconstruction.unknowns`，不要写入已确认结论。

## 更新纪律

- 使用稳定 ID 连接任务、运行、Claim、决策和偏离。
- 不覆盖历史 JSONL 条目；任务状态变化追加完整事件快照，运行状态变化追加新的运行事件。
- `state.yaml` 是当前快照，账本文件是历史证据。
- 所有时间使用带时区的 ISO 8601。
- 写入前展示差异摘要并获得用户确认；写入后执行校验脚本。
