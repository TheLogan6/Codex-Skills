# CVPR 研究执行

## 定位

把 `cvpr-plan` 的阶段节点真实落实为代码、实验、结果和证据。阶段保持研究级粒度；进入阶段后再创建可独立执行和验收的原子任务。

只执行已确认计划及 Goal 允许范围内的工作。不要自行更换代码库、评测协议、目标值、数据划分或研究 IDEA，也不要通过缩小评测对象、降低标准或替换实现来自动绕过阻断。

每次开始或恢复执行前读取：

- [代码与入口规范.md](references/代码与入口规范.md)

- [原子任务与运行证据规范.md](references/原子任务与运行证据规范.md)

- [恢复、偏离与回退规范.md](references/恢复、偏离与回退规范.md)

同时读取项目的 `.cvpr/goal.yaml`、`.cvpr/plan.yaml`、`.cvpr/state.yaml` 和所有账本；需要更新状态时读取 `cvpr-init` 的状态契约。

## 强制前提

开始修改代码或运行实验前确认：

- `goal.yaml.status` 为 `accepted` 或 `revised`；
- `plan.yaml.status` 为 `accepted` 或 `revised`；
- Goal 与 Plan 的用户确认均有效；
- Plan 引用的 Goal 版本和开发基础与实际项目一致；
- 当前阶段依赖均已验收，进入条件已经满足；
- 工作区没有无法区分来源的冲突改动；
- `.cvpr/state.yaml` 已启用执行期状态字段；
- `cvpr_workspace/入口清单.yaml` 已建立或准备按模板建立。

缺失任一项时停止相应执行。旧版状态结构必须先给出迁移差异并按状态契约获得用户确认，不能在内存中临时补字段后继续。

## 执行授权边界

用户调用本 Skill 执行已确认计划后，可在该计划、Goal 和开发基础共同限定的本地范围内：

- 修改研究代码和配置；
- 创建阶段所需的检查、入口、评测包装和分析代码；
- 运行已获准的数据、训练、实验和评测工作；
- 更新 `.cvpr` 执行状态及追加式账本。

以下情况必须暂停并与用户讨论：

- 超出已确认修改范围；
- 需要更换仓库、版本、研究对象、数据或评测协议；
- 需要付费资源、外部发布、远程提交、真实设备或人员参与；
- 存在破坏性操作、不可逆数据处理或不能判定归属的现有改动；
- 结果使 IDEA、Goal 或阶段路径的成立条件发生实质变化。

## 工作流

### 1. 回读并核对真实状态

不要只相信状态摘要。检查真实 Git 版本和工作区、代码、配置、产物、日志、运行进程及账本，判断当前阶段、当前原子任务和最后一个已验收证据。

若这是当前 Plan 的首次执行，先形成执行激活草案：

- 将 `state.yaml` 迁移或确认到 1.1；
- 登记 `active_plan`；
- 按 Plan 全部阶段建立 `stage_statuses` 初始快照；
- 从模板建立 `cvpr_workspace/入口清单.yaml`；
- 将 `execution_workspace.status` 设为 `proposed`；
- 不创建模型专用或其他不适用的空入口。

向用户展示状态与文件差异并确认后再写入。完成激活后运行预检：

运行预检：

```bash
python3 <cvpr-do-Skill目录>/scripts/validate_execution_workspace.py \
  <项目根目录> --mode preflight
```

预检失败时先解决契约或状态问题，不开始研究实现。

### 2. 选择一个可执行阶段

按 Plan 的依赖和顺序选择首个满足进入条件且未验收的阶段。一个时刻只设一个主执行阶段；阶段内部互不冲突的运行可并行，但必须分别登记运行和资源占用。

不要在 `plan.yaml` 中改写执行状态。将活动 Plan、当前阶段和阶段状态快照保存到 `.cvpr/state.yaml`。

### 3. 拆分当前阶段的原子任务

只拆当前阶段，不提前展开整个计划。每个任务必须有单一目标、输入、边界、产物、任务级验收和证据位置，并追加到 `tasks.jsonl`。

任务状态区分：

- `executed`：代码或运行已经产生结果；
- `accepted`：结果通过该任务明确的完成标准；
- 阶段 `accepted`：所有阶段验收规则有证据支持；
- Goal `passed`：所有必需判据和组合逻辑通过正式核验与证据审计。

这些状态不得互相代替。

### 4. 实现并固化可执行代码

研究主体实现放入真实项目的合理代码结构。不要为了统一目录把核心模型、算法或系统实现复制进旁路工作区。

所有影响结果的逻辑必须保存在版本化代码或配置中。禁止只存在于：

- 终端历史；
- `python -c`、shell heredoc 或临时脚本；
- 一次性超长命令参数；
- 未登记的交互式修改；
- 无法定位版本的 notebook 状态。

单次检查、稳定入口、配置、正式核验和分析代码按 [代码与入口规范.md](references/代码与入口规范.md) 统一保存，并登记到 `cvpr_workspace/入口清单.yaml`。

### 5. 保存任务级单次检查

对本次修改建立与风险相称的检查。检查代码统一放入 `cvpr_workspace/checks/`，用于验证局部逻辑、接口、形状、数据变换、数值不变量或本次故障是否修复。

科研开发不默认要求工业项目式的完整测试覆盖、CI/CD 或无关服务化。但与方法、数据、评测和结论有关的路径必须实际可执行。

单次检查通过只能验收相应原子任务或开发条件，不能支持研究效果 Claim，不能标记 `goal_verification` 通过。

### 6. 保留稳定手动入口

入口应采用“稳定代码 + 固定配置”的形式，命令只负责调用入口以及选择配置、checkpoint、恢复点、设备或输出位置等运行态对象。

对于模型研究，必须向用户保留并登记训练、验证和测试三类可手动运行入口。已有仓库入口满足要求时直接登记和复用；缺失时在 `cvpr_workspace/entrypoints/` 建立包装入口。不要复制已有训练框架。

非模型研究只建立实际适用的入口，不创建空的 train/validate/test 脚手架。

### 7. 执行、记录并核对任务

每次运行都登记代码版本、工作区状态、入口、配置、输入、环境、输出、退出状态和证据位置。失败、终止和不支持预期的结果也必须记录。

任务执行后先标记 `executed`，再根据任务完成标准决定 `accepted`、`rejected` 或 `blocked`。不得因命令退出码为零直接写成 `accepted`。

### 8. 执行阶段验收

根据 `stage_validation.kind` 处理：

- `research_development`：核对研究能力、代码产物和必要检查；
- `research_evidence`：核对实验对象、对照、结果和支持强度；
- `goal_verification`：调用 Goal 锁定的协议和真实评测对象；
- `evidence_audit`：逐项统计、交叉核对判据、偏离和证据链。

在正式验证阶段运行：

```bash
python3 <cvpr-do-Skill目录>/scripts/validate_execution_workspace.py \
  <项目根目录> --mode stage
```

只有阶段的全部验收规则有稳定证据时，才把阶段状态写为 `accepted`。

### 9. 核对最终 Goal

所有 `goal_verification` 和 `evidence_audit` 阶段完成后：

1. 逐项读取 Goal 必需判据；
2. 核对协议、数据或对象、实现版本和条件；
3. 汇总原始结果与统计结果；
4. 对每个判据记录 `passed`、`not_met` 或 `indeterminate`；
5. 执行 Goal 的组合验收逻辑；
6. 核对活动偏离和证据缺口；
7. 将结论写入 `state.yaml.goal_assessment`。

结果未达标时如实记录，不修改 Goal 使其通过。最终检查使用：

```bash
python3 <cvpr-do-Skill目录>/scripts/validate_execution_workspace.py \
  <项目根目录> --mode final
```

## 恢复执行

恢复时先核对真实产物、进程和版本，再决定任务状态。存在输出但缺少完成标记时写 `executed` 或 `indeterminate`，不能推断为 `accepted`。

重复运行前确认入口是否幂等、输出目录是否会覆盖已有证据、随机性和恢复点是否受控。需要重跑时创建新的 Run ID，不覆盖旧记录。

## 完成标准

一次阶段执行完成必须同时满足：

- 当前阶段的原子任务均有真实产物和任务级结论；
- 研究实现位于真实项目结构，结果相关逻辑已固化；
- 所需单次检查代码位于统一目录；
- 适用的稳定入口、配置和手动调用方式已经登记；
- 每次运行可追溯到代码、配置、输入、环境和输出；
- 阶段验收规则均有证据；
- 偏离、失败和未支持结果没有被省略；
- `.cvpr` 状态与实际文件、运行和 Plan 一致。

整个 Plan 执行结束后必须通过最终模式校验，并形成 `passed`、`not_met` 或 `indeterminate` 的权威 `goal_assessment`。只有 `passed` 可以报告研究目标已达到；另外两种只能报告“执行完成但 Goal 未通过”或“执行完成但尚不能判定”。

无论 DO 判定为何，完成后都交接给 `$cvpr-result`，由它冻结同一证据包并派出三位独立审稿人进行短流程二次复核。`cvpr-result` 不得改写 DO 判定；若提出挑战，应返回本 Skill 修复并重新判定。
