# 代码与入口规范

## 代码分层

### 研究主体实现

模型、算法、系统、数据管线或实验机制的主体实现放入真实项目已有的合理结构，并遵守项目的依赖和配置约定。不要把主体实现搬入 `cvpr_workspace/` 形成第二套代码。

### 单次检查代码

放入：

```text
cvpr_workspace/checks/
```

用于本次原子任务的局部可执行检查。文件名应能定位阶段、任务或被检查能力。检查应可再次运行，不使用终端临时片段代替。

### 稳定手动入口

优先登记项目已有入口。需要包装时放入：

```text
cvpr_workspace/entrypoints/
```

入口只组织调用、读取固定配置和管理运行对象，不重复实现核心研究逻辑。

### 正式 Goal 核验

需要包装或补充的正式核验代码放入：

```text
cvpr_workspace/goal_evaluation/
```

允许调用官方 evaluator、benchmark 客户端、仿真器、设备协议或人工评价工具，但不得改变 Goal 确认的指标定义、数据对象、阈值、聚合方式或组合逻辑。

### 结果分析

统计、汇总、显著性分析、误差分析和证据表生成代码放入：

```text
cvpr_workspace/analysis/
```

结果分析不得只保留 notebook 的未固化交互状态。使用 notebook 时仍需保存数据输入、环境、执行后的文件和关键逻辑版本。

### 配置

本工作流新增或冻结的运行配置放入：

```text
cvpr_workspace/configs/
```

项目已有配置可以原位保留并登记。配置必须能定位到具体实验目的，不能由一条超长 CLI 覆盖大量结果相关参数。

## 模型研究入口

`research_profile.kind` 为 `model` 或 `mixed` 时必须登记：

- `training`：训练或适配入口；
- `validation`：开发期验证入口；
- `testing`：独立测试或正式测试入口。

三类入口可以引用仓库原有代码，也可以使用工作区包装。它们可以共用同一底层程序，但必须分别给出固定配置、作用和输出边界。

验证入口不天然等于 Goal 核验。只有绑定 Goal 协议与真实对象、登记为 `goal_verification` 范围并产生正式证据时，才能承担最终核验。

## 非模型研究入口

根据实际研究对象登记数据处理、仿真、系统运行、物理实验、人类评价或其他入口。不要为了目录整齐创建无行为的模型入口。

## CLI 边界

手动命令使用参数数组登记，避免依赖 shell 展开。CLI 可以负责：

- 选择已登记配置；
- 选择 checkpoint 或恢复点；
- 选择设备或执行后端；
- 指定输出位置；
- 选择已确认的评测对象。

方法结构、损失、数据划分、关键超参数、指标定义和统计规则等结果相关逻辑应位于代码或配置中。禁止把它们只放在一次性命令中。

## 入口登记

每个入口至少登记：

- 唯一入口 ID 与角色；
- 所属阶段和原子任务；
- 代码路径与配置路径；
- 目的、输入和输出；
- 手动命令；
- 运行参数说明；
- 结果相关逻辑位置；
- 开发检查或 Goal 核验范围；
- Goal 协议与判据引用；
- 当前状态。

入口文件、配置或登记信息变化时更新清单，并保留能够定位旧版本的运行证据。
