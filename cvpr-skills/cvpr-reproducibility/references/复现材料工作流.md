# 复现材料工作流

## 清点单位

以“能够恢复一个关键结果所需的最小完整材料集合”为清点单位，不以文件数量代替完整性。至少检查：

| 类别 | 必查内容 |
|---|---|
| `code` | 代码版本、依赖的本地修改、训练/验证/测试入口、许可证 |
| `config` | 正式运行配置、超参数、预处理、评测协议 |
| `environment` | 操作系统、运行时、库版本、硬件与关键系统依赖 |
| `seed` | 随机源、seed 列表、确定性设置及已知非确定性 |
| `data` | 数据来源、版本、获取方式、处理链、使用许可 |
| `data_split` | train/val/test 或其他划分的身份、生成规则与泄漏检查 |
| `model` | 基座模型、架构版本、来源、修改和许可证 |
| `checkpoint` | 对应 Run、训练阶段、选择标准、完整性标识 |
| `log` | 训练、验证、测试及失败运行的原始日志 |
| `statistics_source` | 输入 Run、分析代码、统计输出和表格源数据 |
| `figure_source` | 图形源数据、绘图代码、导出版本 |
| `third_party_asset` | 外部代码、数据、模型、字体或工具的来源与使用条件 |

## 逆向追踪

对论文每个核心结果执行：

`Claim/表格/图形 → 统计输出 → 原始 Run → 配置与 seed → 代码版本 → 数据及划分 → 环境`

任一边断裂都记录具体缺口、影响范围和需要的证据。不得只写“代码将公开”来替代链路检查。

## 文件与外部材料

- 本地材料记录项目相对路径、大小或校验信息以及生成者。
- 外部材料记录稳定标识、版本、访问日期、访问条件和来源证据。
- 目录存在不等于内容正确；抽查关键文件能否打开并对应冻结快照。
- 对大文件可以记录 manifest 和校验和，不应为审计复制全部内容。
- 对失败 Run 和排除 Run 保留日志及排除理由，避免只发布成功结果。

## 完整性分级

- `complete`：材料已定位、版本明确、关系可追溯、访问与许可已核验。
- `partial`：已有部分证据，但缺少会影响复现或审查的要素。
- `not_applicable`：研究类型确实不需要该类材料，且理由具体。
- `unknown`：尚未确认，不能视作完成。

类别层级的 `complete` 不能仅由一个代表文件推出；要说明该类别覆盖的结果范围。
