# CVPR 最终核验目标

## 定位

把已确认 IDEA 转换为最终核验契约。先确认研究实际基于哪套真实代码、版本和模型或系统开展，再回答“该 IDEA 声称改变什么、应观察到什么”，最后决定使用哪些评测实现、指标或判定规则。

不要重新选择 IDEA，不要设计实现方案，不要展开工程计划。`cvpr-start` 决定研究什么，`cvpr-goal` 决定最后如何核验完成，`cvpr-plan` 再规划如何达到目标。

## 必读规范

开始前读取：

- [核验目标形成流程.md](references/核验目标形成流程.md)
- [评测协议选择规范.md](references/评测协议选择规范.md)
- [目标值确定规范.md](references/目标值确定规范.md)
- [核验契约规范.md](references/核验契约规范.md)

创建或更新 `.cvpr/goal.yaml` 前，同时读取 `cvpr-init` 的 `.cvpr` 状态契约。

## 输入要求

取得以下输入：

- 用户确认的 IDEA、核心假设、预期改变、成立条件和边界；
- `cvpr-start` 形成的文献证据与用户决策；长期项目读取已通过校验且状态为 `accepted` 的 `.cvpr/start.yaml`；
- 用户已有项目、模型、数据、环境或实验条件；没有现成项目时用于调查候选代码库的研究对象和使用条件；
- 用户已知的目标、限制和不可接受结果。

IDEA 尚未确认时返回 `cvpr-start`。长期项目中 `.cvpr/start.yaml` 缺失、无效或未进入 `accepted` 时，不得仅凭 `project.yaml.working_idea` 或某张候选卡自行进入目标固化。

## 工作流

### 1. 拆解待核验主张

将 IDEA 拆为一个或多个可核验主张。对每项主张写清：

```text
研究主张
→ 预期可观察变化
→ 能直接观察该变化的评测对象
→ 可接受的判定规则
→ 最终证据产物
```

不要用方便取得的代理指标替代真正主张。机制主张需要机制证据，真实环境主张需要对应环境证据。

### 2. 确认开发基础

已有项目时，只读检查并向用户确认项目根目录、仓库来源、分支、commit 或等效版本定位、目标模型或系统、拟改动范围，以及它与候选核验协议的兼容性。不要仅凭目录名、README 或用户口头称呼推定代码版本。

没有现成项目时，不得把代码库选择推给 `cvpr-plan`。围绕已确认 IDEA 调查原论文官方仓库、基础模型官方实现、作者维护实现及其他有必要比较的可信候选，核对版本、许可、可执行条件、目标改动位置和评测兼容性；呈报差异并与用户讨论，直到用户明确确认实际采用的代码库与版本。

将结论写入 `development_base`。代码库或版本未确定、真实代码尚不可定位、用户未确认时，契约只能保持 `proposed` 或 `blocked`，不得进入 `cvpr-plan`。

### 3. 确定验证载体

已有项目时，检查项目内与当前主张相关的评测入口、配置、数据或场景、基线记录和结果产物。存在多套实现时比较差异并请用户选择，不自行指定。

开发代码库已确认但其中没有现成核验实现时，围绕实际研究对象调查论文、官方 benchmark、评测服务器、仿真环境、真实实验协议或人类评价方案。锁定来源和版本，并说明它能验证什么、不能验证什么。

验证载体可以是代码、benchmark、模拟器、物理实验、人类评价或混合协议，不假定一定存在本地验证脚本。关键来源不可用时说明阻断，不自动换成未经确认的第三方实现。

### 4. 选择核验判据

只选择能够追溯到当前 IDEA 主张的指标或判断。按实际需要区分：

- 核心验收判据：直接决定 IDEA 是否完成；
- 有效性检查：排除泄漏、配置变化、随机波动或评价偏差；
- 边界约束：仅在 IDEA 或用户明确提出时加入；
- 诊断观察：帮助解释结果，但默认不决定最终验收。

不得预设 mAP、参数量、FLOPs、推理速度、成功率、事实性或其他领域指标。任何判据都必须写明选择理由和来源。

### 5. 确定基线和目标

记录基线是实际测量、官方报告、用户报告还是不适用。选择绝对阈值、相对改进、非劣约束、失败减少、覆盖要求、一致性要求、定性判定或组合逻辑，并给出目标值依据。

不能从文献、基线、统计波动、实际意义或用户约束中得到合理目标时，将目标保留为 `proposed` 并列出缺失证据，不编造数值。

### 6. 与用户确认

向用户同时呈报：

1. 开发代码库候选、来源、版本、目标模型或系统、拟改动范围及评测兼容性；
2. 主张到核验判据的映射；
3. 候选验证载体及版本；
4. 基线来源；
5. 核心验收判据与目标；
6. 有效性检查、边界约束和诊断观察；
7. 仍有争议或无法核验的部分。

用户必须明确确认开发基础、验证载体和最终验收判据。Agent 不能代替用户确认，也不能把“未反对”解释为确认。

### 7. 固化目标契约

项目已存在 `.cvpr/` 时，以 [goal.yaml 模板](assets/核验目标模板/goal.yaml) 写入 `.cvpr/goal.yaml`，并在 `decisions.jsonl` 追加确认决策。写入后运行：

```bash
python3 <cvpr-goal-Skill目录>/scripts/validate_goal_contract.py \
  <项目根目录>/.cvpr/goal.yaml \
  --start-file <项目根目录>/.cvpr/start.yaml
```

没有 `.cvpr/` 时先在对话中完成草案；需要长期写入时调用 `cvpr-init`，不得擅自建立不完整状态目录。

## 状态与变更

- `proposed`：验证载体、目标或用户确认尚未完成；
- `accepted`：契约完整且用户已确认；
- `revised`：经新证据和用户确认替代先前版本；
- `blocked`：关键评测、基线或证据无法获得；
- `rejected`：用户拒绝当前契约；
- `superseded`：被后续契约正式取代。

`cvpr-plan` 只能读取已接受且已确认开发基础的契约，不能选择另一代码库，也不能静默修改目标。执行中需要更换开发基础或变更目标时，提出包含原因、证据和计划影响的修订方案，返回 `cvpr-goal`，由用户确认后再写入新版本。

## 完成标准

- 每个必需验收判据都关联明确主张；
- 真实代码库、版本、项目根目录、目标模型或系统和拟改动范围可定位；
- 开发基础与必需核验协议的兼容性已有证据，且用户明确确认；
- 验证载体、来源、版本、条件和证据产物可定位；
- 基线和目标均有来源，或明确记录不适用理由；
- 指标和约束由 IDEA 推导，没有固定领域预设；
- 验收逻辑能够产生明确的通过、未通过或阻塞结论；
- 所有开放的阻断问题已经解决；
- 用户已明确确认；
- `goal.yaml` 通过校验器。

任一项未满足时不得标记为 `accepted`。

Goal 得到用户确认并通过校验后，将 `$cvpr-plan` 作为下一阶段；由它结合本契约锁定的真实代码库和核验协议形成有序阶段计划。不要在 `cvpr-goal` 内提前拆分开发节点。
