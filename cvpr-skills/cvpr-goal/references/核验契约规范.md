# 核验契约规范

## 根字段

`goal.yaml` 使用 JSON 表达的 YAML 1.2 子集，以便标准库确定性解析。

```text
schema_version
goal_id
idea_id
start_ref
version
status
created_at
updated_at
verification_subject
development_base
evaluation_protocols
baseline
acceptance_criteria
validity_checks
boundary_constraints
diagnostic_observations
acceptance_logic
open_questions
required_artifacts
user_confirmation
supersedes
```

## 研究启动引用

`start_ref` 保存 `start_id`、版本、`.cvpr/start.yaml` 定位和最终 `idea_id`。正式 Goal 只能引用状态为 `accepted`、已经通过 `cvpr-start` 校验器且由用户确认的最终 IDEA。

`goal.yaml.idea_id`、`start_ref.idea_id` 与 `start.yaml.final_idea.idea_id` 必须一致。`project.yaml.working_idea` 只是摘要，不得替代该交叉核验。

## verification_subject

- `research_claims`：一个或多个已确认研究主张；
- `expected_observable_changes`：与主张 ID 对应的预期变化；
- `verification_scope`：契约实际覆盖范围；
- `excluded_scope`：明确不由本契约支持的内容。

## development_base

开发基础用于锁定后续研究实际修改的真实代码，不等同于评测协议。必须包含：

- `project_state`：`existing_project`、`selected_repository` 或草案阶段使用的 `undetermined`；
- `project_root`：可定位的实际项目根目录；
- `repository_url`：远程来源；本地自有项目没有远程仓库时允许为空，但要用来源与版本证据说明；
- `repository_source`：可定位的来源说明，例如远程仓库、用户提供的本地项目或固定归档；
- `repository_source_type`：`user_project`、`official`、`author_maintained`、`community`、`organization`、`other` 或草案阶段的 `undetermined`；
- `branch`：分支上下文；允许 detached HEAD 或非 Git 项目为空；
- `commit`：Git 项目的不可变版本定位；
- `version_or_snapshot`：非 Git 项目的版本、快照或等效定位，也可补充 commit 之外的发行版本；
- `target_model_or_system`：实际准备修改的模型、系统或研究对象；
- `intended_change_scope`：拟改动的模块、机制或范围，不要求预先设计实现；
- `evaluation_compatibility`：兼容的协议 ID、判断说明和证据；
- `user_confirmed`：用户是否明确确认开发基础。

`accepted` 或 `revised` 时：

1. `project_state` 不得为 `undetermined`；
2. `project_root`、`repository_source`、来源类型、目标模型或系统和拟改动范围不得为空；
3. `selected_repository` 必须填写 `repository_url`；
4. 必须使用 `commit` 或 `version_or_snapshot` 提供可复查版本；分支名不能单独替代版本；
5. 必须覆盖所有必需验收判据引用的评测协议，并记录兼容性判断与证据；
6. `user_confirmed` 必须为 `true`。

没有现成项目时先调查候选代码库并取得用户确认，不得把选择责任移交给 `cvpr-plan`。

## evaluation_protocols

每个协议必须包含稳定 ID、类型、来源、版本、实现或流程说明、评测对象、条件、结果产物、关联主张和用户确认状态。

无法用单个版本字段表达时，可在 `conditions` 中记录 commit、数据版本、设备、服务版本或其他必要信息。

## baseline

包含来源类型、协议 ID、条件、结果和证据定位。`not_applicable` 时必须给出非空理由；其他来源必须有至少一项结果和证据。

## acceptance_criteria

每项必须包含：

- `id`；
- `linked_claim_ids`；
- `measure_or_judgment`；
- `target_rule`；
- `target_value`；
- `evaluation_protocol_ids`；
- `evaluation_condition`；
- `selection_rationale`；
- `source_refs`；
- `required`；
- `evidence_artifacts`。

必需判据必须有非空目标、协议、理由、来源和证据产物。

## 其他列表

- `validity_checks`：验证结果可信所需的检查；
- `boundary_constraints`：IDEA 或用户明确要求的边界；
- `diagnostic_observations`：解释结果但默认不参与验收的观察；
- `open_questions`：包含 `blocking` 和 `status`；
- `required_artifacts`：最终验收必须保存的证据。

这些列表允许为空，不得为了模板完整性填入不相关内容。

## 用户确认

```json
{
  "status": "pending",
  "confirmed_at": null,
  "confirmed_by": null,
  "evidence_ref": null
}
```

`accepted` 或 `revised` 时必须为 `confirmed`，并填写时间、确认者和证据定位。开发基础必须由用户确认；至少一个评测协议需要明确由用户确认，所有必需判据引用的协议都必须确认。

## 版本与修订

- 新建契约从 `version: 1` 开始；
- 已确认内容改变时递增版本；
- `revised` 契约填写 `supersedes`；
- 在 `decisions.jsonl` 追加变更原因、证据和用户确认；
- 不覆盖旧契约的历史证据，可将旧版本归档到项目约定位置。
