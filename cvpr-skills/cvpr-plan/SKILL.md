# CVPR 阶段计划

## 定位

把已确认 IDEA 和 `goal.yaml` 映射到真实代码，形成有序的阶段节点。每个节点表达一段完整科研开发或验证目的；具体命令、局部修改和原子任务留给后续 `cvpr-do` 在进入阶段时生成。

只规划和修订计划，不修改研究代码、不运行实验、不替换代码库、不改变 Goal。

## 必读规范

开始前读取：

- [阶段节点规范.md](references/阶段节点规范.md)

- [计划契约规范.md](references/计划契约规范.md)

同时读取 `cvpr-init` 的状态契约、项目 `.cvpr/goal.yaml` 和 `cvpr-someagents`。

## 强制前提

开始正式规划前确认：

- IDEA 已由用户确认；
- `goal.yaml.status` 为 `accepted` 或 `revised`；
- `development_base.user_confirmed` 为 `true`；
- 项目根目录、真实代码来源、不可变版本、目标模型或系统和拟改动范围可定位；
- 必需验收判据和真实评测协议已经确定。

任一项缺失时停止规划。代码库缺失、版本不清或用户未确认时返回 `cvpr-goal`，不得由 `cvpr-plan` 选择开发基础。

## 工作流

### 1. 读取真实项目

只读检查 Goal 锁定的代码版本，建立 IDEA、目标主张、实际代码结构、数据或环境和核验协议之间的对应关系。记录已检查的文件、配置、调用链、既有结果和事实证据。

README、目录名和预期架构不能代替真实代码。代码实际与 Goal 不一致时立即与用户讨论；需要换库、换版本或改核验协议时返回 `cvpr-goal`。

### 2. 建立目标覆盖关系

对每个必需验收判据回答：

```text
达到该判据需要完成哪些阶段
→ 哪个阶段形成研究实现
→ 哪个阶段形成支持证据
→ 哪个阶段执行 Goal 锁定的真实核验
→ 最终保存什么证据
```

没有阶段覆盖的必需判据必须补齐，不能留给执行 Agent 自行发现。

### 3. 形成阶段节点草案

按研究实际建立有序节点。节点可覆盖代码分析、研究实现、数据或环境准备、实验、真实评测、统计和证据审计，但不使用固定阶段模板强迫所有项目执行相同内容。

节点必须具有阶段目的、依赖、进入条件、实际代码或研究范围、阶段产物、验收标准和证据产物。禁止写时间预估、工期、排期或日历承诺。

### 4. 区分开发检查与真实验证

代码能够加载、导入、启动或处理少量样例，只能作为阶段内部的开发检查，不能成为研究验证节点的完成证据。

`goal_verification` 节点必须在 Goal 确认的数据集划分、benchmark、仿真、物理实验、人类评价或其他真实评测对象上执行锁定协议，并直接引用 Goal 的验收判据。完整要求见 [真实验证节点规范.md](references/真实验证节点规范.md)。

### 5. 强制多 Agent 审查

形成初步计划后调用通用 `cvpr-someagents` 模式 B。所有 Agent 接收同一版本的 IDEA、Goal、代码证据和计划草案，分别审查代码一致性、科研路径、Goal 覆盖、实验有效性、真实验证和工程适度性。

阻断问题未解决、审查记录不完整或少于两个独立 Agent 视角时，不得向用户呈报计划。

### 6. 与用户讨论

将审查后的初步计划、关键证据、审查分歧和开放问题呈报用户。用户可以调整阶段边界、顺序、验收、允许修改范围和决策点。

规划过程中任何无法从 Goal 或真实代码裁决的问题都应立即跳出讨论，不自行补齐。用户未明确确认前，不创建或覆盖项目 `.cvpr/plan.yaml`，也不向 `tasks.jsonl` 写入执行任务。

### 7. 固化正式计划

用户确认后，以 [plan.yaml 模板](assets/阶段计划模板/plan.yaml) 写入项目 `.cvpr/plan.yaml`，在 `decisions.jsonl` 追加确认决策，并运行：

```bash
python3 <cvpr-plan-Skill目录>/scripts/validate_plan_contract.py \
  <项目根目录>/.cvpr/plan.yaml \
  --goal-file <项目根目录>/.cvpr/goal.yaml
```

校验未通过时保持草案或阻塞状态，不写成已接受计划。

## 阶段与原子任务

`plan.yaml` 保存长期阶段节点、顺序、依赖和验收，并作为用户确认后的规划基线。阶段开始执行时，`cvpr-do` 再把当前节点拆为原子任务并追加到 `tasks.jsonl`；实际阶段状态写入 `state.yaml.stage_statuses`，不以日常进度改写正式 Plan。

不要在规划阶段提前生成大量命令级任务。阶段节点完成不等于整个 Goal 完成；只有最终核验和证据审计满足 `goal.yaml` 才能形成完成结论。

## 科研工程边界

根据研究证据链决定必要的代码检查，不照搬工业项目的完整单元测试、覆盖率、CI/CD 或服务化体系。与方法逻辑、数据处理、评测和结论有关的代码必须有效、可执行、可追溯；与研究无关的工程化不进入计划。

## 计划变更

执行中需要改变阶段路径但不改变 Goal 时，先提出计划修订、说明证据和影响，与用户讨论后生成新版本。涉及代码库、研究对象、核验协议或目标值时返回 `cvpr-goal`。

计划不得自动缩减阶段、降低验收、替换真实评测或用开发检查代替验证。

## 完成标准

- Goal 和开发基础满足全部前提；
- 阶段来自真实代码和研究需要，不是通用模板；
- 顺序、依赖、进入条件和阶段边界明确；
- 所有必需 Goal 判据均有阶段覆盖和真实核验节点；
- 验证节点引用真实协议、评测对象和证据产物；
- 没有时间预估和工业式过度测试要求；
- `cvpr-someagents` 审查完成且阻断问题已解决；
- 用户已明确确认；
- `plan.yaml` 与 `goal.yaml` 联合校验通过。

完成后明确交接给 `$cvpr-do`。首次执行由 `cvpr-do` 建立执行期状态和 `cvpr_workspace/入口清单.yaml`，再开始当前阶段；不得在本 Skill 内直接开始执行。
