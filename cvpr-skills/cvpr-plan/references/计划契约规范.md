# 计划契约规范

## 根字段

`plan.yaml` 使用 JSON 表达的 YAML 1.2 子集：

```text
schema_version
plan_id
version
status
created_at
updated_at
goal_ref
development_base_ref
planning_basis
global_boundaries
stages
criterion_coverage
someagents_review
open_questions
user_confirmation
supersedes
```

`accepted` 表示阶段计划契约已经用户确认，不表示研究已经完成。`plan.yaml` 中的节点状态是确认时的初始状态；实际阶段状态保存在 `.cvpr/state.yaml.stage_statuses` 及追加式账本中。

## Goal 引用

`goal_ref` 必须包含 Goal ID、版本、状态、文件定位、必需判据 ID 和协议 ID。正式计划校验时同时加载 `goal.yaml`，不得手工复制后脱离来源。

`development_base_ref` 保存 Goal 中已确认开发基础的稳定定位。正式计划必须与 Goal 的项目根目录、版本和目标模型或系统一致。

## 阶段

阶段字段遵守 [阶段节点规范.md](阶段节点规范.md)。至少需要一个 `goal_verification` 节点和一个 `evidence_audit` 节点；同一阶段可以覆盖多个 Goal 判据。

## Goal 覆盖

```yaml
criterion_coverage:
  - goal_criterion_id: AC-001
    supporting_stage_ids: []
    verification_stage_ids: []
    evidence_artifacts: []
```

每个 Goal 必需判据都必须有至少一个 `goal_verification` 阶段。支持阶段允许为空，真实验证阶段不得为空。

## 多 Agent 审查

`someagents_review` 保存模式、输入计划版本、独立角色结果、协调后的 `final_verdict`、阻断问题、已解决问题和证据定位。正式计划至少需要两个独立 Agent 结果，不存在未解决阻断，且最终结论必须为 `pass`。

## 用户讨论和确认

开放问题包含问题、是否阻断和状态。正式计划不能保留开放的阻断问题。

用户确认包含状态、确认时间、确认者和证据定位。`accepted` 或 `revised` 时必须为 `confirmed`。

## 修订

- 初版 `version` 为 1；
- 阶段边界、顺序或验收变化时递增版本；
- `revised` 必须填写 `supersedes`；
- 改变代码库、研究对象、协议或 Goal 判据时返回 `cvpr-goal`；
- 不覆盖旧计划的决策和执行证据。
- 不为记录日常执行进度而改写正式 Plan；只有阶段设计本身变化时才创建修订版本。
