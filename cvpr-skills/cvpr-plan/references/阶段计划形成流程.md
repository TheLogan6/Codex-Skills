# 阶段计划形成流程

## 一、前置核对

读取 `goal.yaml`，确认状态、版本、开发基础、必需验收判据和协议。以下情况停止并返回 `cvpr-goal`：

- 没有真实项目根目录；
- 开发代码库或版本未确定；
- `development_base.user_confirmed` 不是 `true`；
- 目标模型、系统或拟改动范围不明确；
- 代码库与必需评测协议的兼容性没有证据；
- Goal 仍有开放的阻断问题。

## 二、代码与研究映射

只读检查真实代码并形成：

```text
IDEA 主张
→ 相关模型、系统、数据或环境
→ 实际代码位置和调用关系
→ 需要形成的研究变化
→ 支持该变化的实验与证据
→ Goal 对应验收判据
```

只保存能够定位的事实。无法确认的实现路径写入开放问题并与用户讨论。

## 三、阶段划分

用阶段节点表达完整研究目的，不按函数、文件、命令或一次运行划分。一个阶段应满足：

- 能说明它为哪个研究主张服务；
- 有明确的进入条件和阶段产物；
- 能通过研究证据、实际代码结果或真实评测结果验收；
- 完成后能够合理进入下一阶段；
- 内部仍可由 `cvpr-do` 拆为多个原子任务。

阶段数量服从研究实际，不凑固定数量。

## 四、初步计划审查

计划草案形成后先调用 `cvpr-someagents`，使用 [多Agent计划审查协议.md](多Agent计划审查协议.md) 的同一证据包和多角色标准。协调者修订草案并保留少数派实质风险。

## 五、用户讨论

呈报：

1. Goal 到阶段的覆盖关系；
2. 每个阶段的目的、依赖、实际范围和验收；
3. 真实验证阶段采用的对象和协议；
4. 多 Agent 审查发现和处置；
5. 仍需用户决定的问题。

用户确认前只在对话中维护草案。不得提前写入项目正式 `plan.yaml`。

## 六、正式写入

用户明确确认后写入 `plan.yaml` 和决策记录。不要在此时填充 `tasks.jsonl`；原子任务属于 `cvpr-do` 进入具体阶段后的执行记录。
