# CVPR Someagents — 多 Subagent 并行编排

## 定位与注册

这是 `cvpr-skills` 包内的通用原子 Skill，不属于任何单一阶段，也不默认等同于“候选 IDEA 呈报前审查”。任何上层流程都可以按需调用它；调用方负责声明任务目标、输入范围、完成标准和需要回写的 `.cvpr/` 状态。

当 `cvpr-start` 在候选 IDEA 呈报前调用本 Skill 时，强制审查、角色集合和通过门槛由 `cvpr-start` 定义。本 Skill 只负责正确编排和执行多 Agent 协作，不把该特例扩展为自身的全局触发条件。

如果当前项目存在 `.cvpr/`，协调者在调用结束后记录参与 Agent、模式、输入包版本、各自结论、分歧、最终裁决和证据位置。没有 `.cvpr/` 时仍可独立运行，不得为了注册状态阻断原子任务。

只有实际创建并完成的独立 Agent 才能计入审查或投票数量。必须保存真实 Agent 标识、输入快照、独立性、完成状态和原始输出定位；不得由协调者在单次推理中模拟多个身份后声称完成多 Agent 审查。调用方要求恰好三位或规定最低数量时，资源不足即报告阻断，不得静默减少数量。

## 概述

用多个 subagent 并行工作时，核心问题不是"能不能并行"，而是**"用什么模式并行"**。模式选错，要么浪费时间，要么结果冲突。

四种模式覆盖所有并行场景：

```
A. 独立问题域 — 问题天然不同，各自解决，事后汇总
B. 多角色分析 — 同一事物，不同角度，互补汇总
C. 分工协作   — 协调者拆解任务，分配子任务，过程整合
D. 独立分析+投票 — 同一问题，同角度独立分析，投票定论
```

## 决策树

```
你需要多 subagent 并行工作
│
├─ 任务是解决多个不同问题？
│   ├─ 是 → 模式 A（独立问题域）
│   └─ 否 → 继续
│
├─ 任务是分析/审查/评估，还是实现/构建/写作？
│   │
│   ├─ 分析/审查/评估 ──→ 继续
│   │   ├─ 需要从不同专业角度看？ → 模式 B（多角色分析）
│   │   ├─ 需要多人独立判断达成共识？ → 模式 D（独立分析+投票）
│   │   └─ 需要各自探索找根因？ → 模式 A 变体（根因排查）
│   │
│   └─ 实现/构建/写作 ──→ 继续
│       ├─ 子任务修改相同文件或有依赖？ → 不要并行，串行执行
│       └─ 子任务修改不同模块且无依赖？ → 模式 C（分工协作）
```

## 模式 A：独立问题域

### 适用场景

多个**天然不相关**的问题，各自独立解决，互不依赖。

典型场景：
- 修复 3 个不同模块的 bug
- 同时处理多个独立的数据处理任务
- 对多个独立代码文件进行不同修改

### 信息流

- 每个 agent 只拿到**自己问题域的相关上下文**
- 不需要了解其他 agent 在做什么
- 不需要全局视图

### 执行流程

```
第 1 轮：并行派发 agent，各自解决各自的问题
第 2 轮：协调者事后整理、去重、汇总所有结果
```

### 变体：根因排查

同一故障/异常，多个 agent 各自独立从头探索，不给方向暗示。

- 所有 agent 拿到**原始故障信息**（日志、错误信息、相关代码范围）
- 各自独立探索，互不影响
- 最后对比各 agent 的根因结论，找共识和矛盾

## 模式 B：多角色分析

### 适用场景

同一个事物，需要从**不同专业角度**分析，产出互补性见解。

典型场景：
- 设计方案评审（架构角度 / 安全角度 / 性能角度 / 可维护性角度）
- 论文审稿（方法 / 实验 / 写作 / 图表 各角度）
- 技术方案评估（可行性 / 成本 / 风险 / 可扩展性）

### 信息流

- 所有 agent 拿到**相同的完整上下文**
- 每个 agent 额外拿到**自己的角色提示**（专业视角、关注点）
- 角色提示决定关注什么，不改变理解的信息本身

### 执行流程

```
第 1 轮：并行派发各角色 agent，分析同一事物
第 2 轮：协调者汇总各角色产出，去重，整合为互补的完整分析
```

### Agent 配置要点

- 每个 agent 的角色定义要明确：专业领域、关注维度、评判标准
- 角色之间不重叠（重叠会造成冗余）
- 角色之间不留空白（空白意味着漏掉视角）

## 模式 C：分工协作

### 适用场景

一个任务太大，协调者**主动拆解**为子任务，分给不同 agent 完成子部分。

典型场景：
- 写一篇专栏（资料收集 agent → 撰写 agent → 润色 agent）
- 构建多模块项目（模块 A agent + 模块 B agent，模块间接口已约定）
- 数据处理流水线（采集 → 清洗 → 分析，但清洗依赖采集结果则不能并行）

### 信息流

- 协调者**预先消化**整体信息
- 为每个 agent **定制化信息包**：只给完成子任务所需的部分
- 每个 agent 不需要看到全局，避免信息过载

### 执行流程

```
第 0 轮：协调者分析任务，拆解子任务，定义输出契约
第 1 轮：并行派发各子任务 agent（仅当子任务无依赖时）
第 2 轮：协调者整合各 agent 输出，一致性检查，交付最终结果
```

### 关键约束

- 子任务**不能有依赖关系**（B 需要 A 的输出 → 不能并行）
- 子任务**不能修改相同文件**（会导致冲突）
- 协调者必须**明确定义每个 agent 的输出契约**

## 模式 D：独立分析 + 投票

### 适用场景

同一个问题，多个 agent **同角度独立分析**，通过投票达成共识。

典型场景：
- PR 代码审查（3+ agent 独立审查同一 diff，投票：通过/需修改）
- 方案可行性判断（多 agent 独立评估，投票：可行/不可行/有条件可行）
- 内容质量评估（多 agent 独立打分，取平均或多数）

### 信息流

- 所有 agent 拿到**完全相同的精选信息包**
- 所有 agent 拿到**完全相同的评判标准**
- 不给任何 agent 额外的提示或偏向（保证公平投票）

### 执行流程

```
第 1 轮：并行派发 agent，各自独立分析同一内容
第 2 轮：协调者去重、归类所有发现
第 3 轮：3 个投票 agent 审查第 2 轮的结果，各自投票
第 4 轮：协调者统计票数，关注少数派意见理由，汇报最终结论
```

### Agent 配置要点

- 投票 agent 的角色和评判标准必须一致
- 投票结论需要附带理由（单纯赞成/反对没有参考价值）
- 少数派意见不能忽略（可能包含关键风险点）

## 信息流决策指南

subagent 该拿什么信息？取决于模式：

| 模式 | 信息策略 | 原因 |
|------|---------|------|
| A 独立问题域 | 各自问题域的上下文 | 只需解决自己的问题 |
| A 变体根因排查 | 原始故障信息，不给方向 | 避免锚定，自主探索 |
| B 多角色分析 | 相同完整上下文 + 各自角色提示 | 角色提供差异化视角 |
| C 分工协作 | 协调者定制化信息包 | 只给所需，避免过载 |
| D 投票 | 相同精选信息 + 相同评判标准 | 公平基准，可比结果 |

### 预消化 vs 原始信息

**给原始信息**：当你希望 agent 自主探索、不被你的判断影响时
- 根因排查、开放性分析、探索性研究

**给精选信息**：当你需要 agent 在特定范围内做判断时
- 代码审查（给 diff 不给全项目）
- 投票决策（给关键信息不给噪音）
- 角色分析（给完整上下文但通过角色提示聚焦）

**给定制信息**：当 agent 只需要完成局部任务时
- 分工协作中的子任务 agent
- 每个 agent 信息包不同

## 红牌规则

- **实现类任务修改相同文件 → 禁止并行**，必须串行，否则合并冲突
- **可独立分析的任务 → 在并发资源可用且不破坏独立性时并行**，资源不足时明确报告
- **同一组 agent 不可混用模式**，要么都独立分析，要么都分工协作
- **投票 agent 必须拿到完全相同的信息包**，否则投票结果不可比
- **分工协作前必须明确输出契约**，否则整合时无法对齐
- **根因排查不要给方向暗示**，否则所有 agent 可能被锚定到同一个错误方向
- **实际 Agent 数量不足 → 明确阻断**，不得用角色扮演或协调者自审补足名额

## 模式速查

| 我想... | 用模式 |
|---------|--------|
| 同时修几个不相关的 bug | A |
| 找某个难复现 bug 的根因 | A 变体 |
| 从架构/安全/性能角度评审设计 | B |
| 让多个 agent 一起写一个大项目 | C |
| 审查 PR 是否应该合入 | D |
| 判断一个技术方案是否可行 | D |
